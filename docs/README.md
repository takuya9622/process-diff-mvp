## 管理方針

- 原則として日本語で記載する。
- 決定事項と仮説、未決事項を区別する。
- 実装の変更に合わせて、関連する設計書も更新する。
- ユーザー固有の環境情報や非公開情報は記載しない。

## トークン効率を考慮した分割基準

### 基本原則

- AIと人間が、現在の作業に必要な文書だけを読める構造を優先する。
- 一つのファイルへ無関係な話題を集約せず、独立して参照・更新できる単位は
  ディレクトリと複数ファイルへ分割する。
- ファイル数を増やすこと自体を目的にしない。分割によって前提説明、リンク移動、
  読み込みファイル数が増える場合は、一つのファイルに保つ。
- 行数やファイルサイズは判断のきっかけとして使い、数値だけで自動的に分割しない。

### 分割を推奨する条件

次の条件のうち、複数に該当する場合は分割を積極的に検討する。

1. 一つのファイルに、要件、ドメイン、画面、API、運用など独立した主題が複数ある。
2. 主題ごとに参照する利用者、作業、更新タイミングが異なる。
3. 通常の作業では、ファイル全体の半分未満しか参照しないことが多い。
4. 一部の章だけが頻繁に更新され、ほかの章は安定している。
5. ディレクトリの`README.md`から、必要な文書を迷わず選べる境界がある。
6. 目安として400行または20KBを超え、さらに内容が複数の主題に分かれている。

700行または35KBを超えるファイルは、全体を常に一緒に読む必要がある明確な理由が
ない限り、分割を強く推奨する。

### 一つのファイルに保つ条件

次のいずれかに該当する場合は、不必要に分割しない。

1. 内容が一つの判断、仕様、または連続した説明として常にまとめて参照される。
2. 分割後の各ファイルが短く、単独では意味を理解できない。
3. 共通の前提を複数ファイルへ繰り返し記載する必要がある。
4. 一つの作業を理解するために、毎回多数のファイルを順番に開く必要がある。
5. 分割による読み込み量の削減より、索引確認と文脈復元の負担が大きい。

100行未満の文書を複数作る場合は、それぞれが独立して参照または更新される理由があるか
確認する。理由がなければ、同じ主題の文書へまとめる。

### 分割するときの構造

主題を分割する場合は、次の構造を基本とする。

```text
docs/
└── <topic>/
    ├── README.md
    ├── overview.md
    └── <subtopic>.md
```

- `<topic>/README.md`には、主題の概要、文書一覧、各文書を読む条件、現在の状態を記載する。
- 詳細は各文書に一度だけ記載し、索引や別文書では要約とリンクだけを置く。
- 共通用語や前提は入口の`README.md`へ集約し、各文書で重複させない。
- 一般的な作業で、入口の`README.md`と1〜2ファイルを読めば必要な文脈が揃う構造を目指す。

### 見直し手順

文書を追加または大きく更新するときは、次の順で判断する。

1. その文書を読む代表的な作業を挙げる。
2. 各作業で必要になる章を確認する。
3. 独立して参照・更新できる境界があるか確認する。
4. 分割後に重複する前提や、毎回読む必要があるファイル数を見積もる。
5. 必要な読み込み量が減る場合だけ分割する。
6. 分割した場合は、このファイルのドキュメント一覧と対象ディレクトリの`README.md`を更新する。
