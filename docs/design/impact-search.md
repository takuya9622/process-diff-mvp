# 影響候補の探索仕様

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 文書状態 | 初期決定 |
| 対象 | 変更した業務要素から影響候補と関係経路を算出するMVP仕様 |
| 最終更新日 | 2026-08-09 |

この文書では、登録済みの`BusinessEntity`と`Relation`から、再現可能な影響候補を算出する
規則を定義します。基準となるグラフと期待結果は
[サンプル業務と検証シナリオ](sample-business-scenario.md)、データの意味は
[ドメインモデルと影響判定要件](../requirements/domain-and-impact.md)を参照してください。

## 2. MVPの決定

| 項目 | 決定 |
|---|---|
| 探索方式 | 幅優先探索（BFS） |
| 関係の向き | 登録方向を保持したまま、探索は両方向へ行う |
| 最大深度 | 2 |
| 対象関係 | MVPで定義したすべての関係種別 |
| 重複 | 業務要素ID単位で除外する |
| 経路 | 最短経路を一つ採用する |
| 並び順 | 距離、業務要素の種類、名称、IDの順 |
| 保存 | 保存せず、確定済みの変更元と現在の関係から都度算出する |
| 重要度 | 重み付きスコアを作らず、直接関係と2段階先を区別する |

MVPでは、関係の向きだけから影響の有無を断定できないため、incomingとoutgoingの両方を
探索します。たとえばルールを変更した場合、そのルールが従う規程と、そのルールに従う業務の
どちらも確認対象になり得ます。

## 3. 入力と出力

### 3.1 入力

- 変更を確定した`ChangeSet`
- 変更対象の`business_entity_id`
- 現在の`BusinessEntity`
- 現在の`Relation`
- 最大深度`2`

未確定の変更案から影響候補をプレビューする処理は、MVPへ含めません。

### 3.2 出力

候補ごとに、最低限次を返します。

| 値 | 内容 |
|---|---|
| `entity` | 候補となった業務要素 |
| `distance` | 変更元からの関係数。`1`または`2` |
| `path` | 変更元から候補までの要素と関係の並び |
| `reason` | 候補になった理由を利用者向けに表現した情報 |

`ImpactCandidate`は永続化用テーブルにせず、同じ入力から同じ結果を再生成できる算出値として
扱います。

## 4. 探索手順

1. すべての`Relation`から、sourceとtargetの双方を隣接要素として参照できる隣接リストを作る。
2. 各隣接情報には、元のsource、target、関係種別、探索時の向きを保持する。
3. 変更元を距離`0`としてqueueへ追加する。
4. 隣接情報を決定的な順序に並べ、幅優先で探索する。
5. 初めて到達した距離を候補の最短距離とする。
6. 距離`2`へ到達した要素から先は探索しない。
7. 変更元自身を候補へ含めない。
8. 同じ要素へ複数経路で到達した場合は一件へまとめ、経路選択規則に従って一経路を採用する。
9. 候補表示の並び順を適用し、理由を組み立てる。

cycleを含むグラフでも、訪問済みの要素と距離を管理して無限に探索しません。

## 5. 決定的な順序

同じデータから常に同じ候補と経路を返すため、データベースの返却順へ依存しません。
この文書内の名称比較は、Unicode NFCへ正規化した後、
`Intl.Collator("ja", { numeric: true, sensitivity: "variant" })`を使用します。

### 5.1 関係種別の順序

同じ長さの経路を比較するため、関係種別へ次の固定順を設定します。これは実際の影響度を
示す重みではなく、結果を再現するためのtie-breakerです。

1. `GOVERNED_BY`
2. `REFERENCES`
3. `REQUIRES`
4. `USES`
5. `PRODUCES`
6. `APPROVED_BY`
7. `OWNED_BY`

同じ関係種別では、登録方向への探索、登録方向と逆向きの探索、隣接要素の種類、名称、IDの順で
比較します。

### 5.2 業務要素の種類の順序

候補は距離が短いものを先にし、同じ距離では次の種類順に表示します。

1. `PROCESS`
2. `RULE`
3. `DOCUMENT`
4. `SYSTEM`
5. `ROLE`

同じ種類では名称の昇順、名称も同じ場合はIDの昇順とします。種類順は確認作業の入口として
業務とルールを先に見せるための表示判断であり、影響の確率を表しません。

## 6. 経路の選択

- 最短距離が異なる場合は、短い経路を採用する。
- 最短距離が同じ場合は、経路を構成する関係種別の順序を先頭から比較する。
- 関係種別も同じ場合は、探索方向、途中の要素の種類、名称、IDを順に比較する。
- 採用しなかった経路はMVPの画面へ表示しない。

複数経路の一覧が利用者の判断に必要だと分かった場合に、表示と出力形式の拡張を検討します。

## 7. 利用者向けの関係表現

enumをそのまま表示せず、元のsourceとtargetの向きを保った文章またはステップとして表示します。

| 関係種別 | 基本表現 |
|---|---|
| `REQUIRES` | `<source>は<target>を前提とする` |
| `REFERENCES` | `<source>は<target>を参照する` |
| `GOVERNED_BY` | `<source>は<target>に従う` |
| `USES` | `<source>は<target>を使用する` |
| `OWNED_BY` | `<source>は<target>が担当する` |
| `APPROVED_BY` | `<source>は<target>が承認する` |
| `PRODUCES` | `<source>は<target>を生成する` |

候補一覧では、距離`1`を「直接関係」、距離`2`を「2段階先の関連項目」と表現します。
「高影響」「低影響」のような確度を断定するラベルは付けません。

## 8. 関係経路の表示

MVPでは、業務グラフ全体ではなく、採用した一経路をステップ表示します。

- 変更元を最初に表示する。
- 各ステップに関係の文章と次の業務要素を表示する。
- 登録方向と逆向きに探索した場合も、文章は元のsourceとtargetの向きで表示する。
- 色だけに依存せず、要素名、種類、関係文を表示する。
- 距離`2`では、途中の業務要素を省略しない。

簡易グラフは、ステップ表示では経路を理解できないことが検証で確認された場合だけ追加します。

## 9. 基準シナリオの期待値

`rule-receipt-requirement`を変更元とした場合、次を返します。

- 距離`1`: `process-expense-submission`、`process-receipt-review`、
  `document-expense-policy`、`document-expense-manual`
- 距離`2`: `process-reimbursement-payment`、`rule-approval-threshold`、
  `system-expense`、`role-accounting`、`role-approver`、`role-applicant`
- 対象外: 変更元自身、距離`3`の`system-accounting`

具体的な表示名と代表経路は
[サンプル業務と検証シナリオ](sample-business-scenario.md)を正本とします。

## 10. 必須テスト

- outgoing relationを探索できる。
- incoming relationを逆向きに探索できる。
- 距離`2`まで探索し、距離`3`を含めない。
- cycleがあっても終了する。
- 変更元自身を含めない。
- 同じ候補へ複数経路で到達しても一件だけ返す。
- 複数の最短経路から決定的に一経路を選ぶ。
- relationとentityの取得順を変えても、候補、順序、経路が変わらない。
- 基準シナリオで距離`1`の4件、距離`2`の6件を返す。

## 11. 見直し条件

次のいずれかが確認された場合に、深度、関係種別、重み、複数経路表示を見直します。

- 候補が多すぎて、確認対象を判断できない。
- 必要な候補が距離`3`以降に集中する。
- 関係種別によって確認優先度を変えないと利用者が迷う。
- 採用した一経路だけでは候補理由を説明できない。
- サンプル以外の業務領域で、両方向探索による誤検知が多い。

MVP検証前に、将来利用だけを理由として探索深度や重みを追加しません。
