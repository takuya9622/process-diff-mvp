## 3. 自動化との境界

- ESLint、Prettier、TypeScript、`prettier-plugin-tailwindcss`が自動的に検出または修正する
  インデント、引用符、改行、セミコロン、Tailwind classの並び順などは、この規約へ重ねて
  記載しない。
- 機械的に検査できる新しい規則が必要になった場合は、文章だけで運用せず、設定またはテストで
  検出できるかを先に検討する。
- 自動化できない責務境界、命名の意味、設計意図、例外条件を、この規約で管理する。
- ツールの設定を変更した場合は、必要に応じて
  [Linter・Formatter設計](../linting-and-formatting.md)も同時に更新する。

## 4. コメント

コードを読めば分かる動作をコメントで説明しません。コメントがなくても意図が伝わる命名、
関数分割、型、データ構造を優先します。

コメントを使用できるのは、コードだけでは次の情報を十分に表現できない場合です。

- 採用した実装の理由と、選ばなかった方法の制約
- 外部仕様、ブラウザ、ライブラリ、データ互換性による回避策
- 壊してはならない業務上の不変条件
- 一見不要に見える処理を残す理由
- 一時対応の終了条件または削除条件

次のコメントは記載しません。

- 直後の処理を日本語または英語で読み替えただけの説明
- 関数名、変数名、型名で表現できる内容
- ファイルや処理を見出しとして区切るだけのコメント
- 実装と同時に更新される保証のない変更履歴
- 理由、担当範囲、終了条件が分からない`TODO`

コメントが必要になった場合も「何をしているか」ではなく「なぜ必要か」を短く記載します。

## 5. 読みやすさと責務

- 一つのファイルには、一つの主要な責務を持たせる。
- 名前は実装手段ではなく、業務上または画面上の役割を表す。
- 略語や汎用名を避け、呼び出し側で役割を推測しなくてよい名前にする。
- 関数は一つの判断または処理単位へ絞り、条件分岐が複雑になった場合は、意味のある単位へ
  分解する。
- 重複をなくすことだけを目的に、責務や依存方向が異なるコードを共通化しない。
- 抽象化は、複数の利用箇所で同じ意味と変更理由を持つことを確認してから行う。

## 6. ファイルとディレクトリの分割

行数だけを一律の上限にはしません。ただし、次のいずれかに該当する場合は、ファイルが
肥大化する前にディレクトリとファイルの分割を検討します。

1. 複数の独立した責務、画面状態、データ変換を一つのファイルが扱っている。
2. 変更時に、対象と無関係なコードを広く読み直す必要がある。
3. テスト、型、定数、表示ロジックの一部を独立して再利用または検証できる。
4. 機能追加のたびに同じファイルへ条件分岐や状態が増える見込みがある。
5. ファイル名だけでは内容の範囲を説明できなくなっている。

分割するときは、意味のない連番や`utils`への集約ではなく、機能、画面状態、ドメインなど
変更理由が揃うディレクトリを作ります。小さなファイルを増やしすぎて、常に多数のファイルを
往復しなければ一つの処理を理解できない構造も避けます。

## 7. レビュー時の確認

- コメントがコードの読み替えではなく、コードだけでは表現できない意図を説明しているか。
- ファイルに複数の主要責務が混在していないか。
- 今後の追加で肥大化しやすい箇所に、意味のある分割境界があるか。
- 共通化によって依存方向が逆転したり、変更理由が異なるコードが結合していないか。
- LinterやFormatterが処理する表記を、人手のレビュー項目として重複させていないか。
