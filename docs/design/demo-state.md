# 公開デモの状態管理

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 文書状態 | 初期決定 |
| 対象 | 認証なしで公開するMVPの状態共有、競合、リセット |
| 最終更新日 | 2026-08-09 |

この文書では、公開URLを複数の利用者が開いた場合の状態単位と、変更競合、サンプルリセットを
定義します。永続化する構造は[MVPテーブル設計](table-design.md)、画面上の注意と操作は
[MVP画面構成とユーザーフロー](screens-and-user-flow.md)を参照してください。

## 2. MVPの決定

初期MVPは、すべての利用者が一つの共有サンプル状態を参照・変更する構成とします。

- 認証、利用者、組織、匿名workspaceのテーブルを追加しない。
- `BusinessEntity`、`Relation`、`EntityVersion`、`ChangeSet`は一組だけ保持する。
- 確定した変更は、別のブラウザからも同じ現在状態と履歴として見える。
- ブラウザやcookieごとの状態分離は行わない。
- サンプルリセットは、共有状態全体へ作用する。

公開デモとしての完全な分離より、MVPの中核価値である変更、差分、影響候補を最小の構造で
検証することを優先します。評価URLは、初期MVPの間は管理可能な人数へ共有します。

## 3. 画面上の明示

ヘッダーまたは編集開始前に、次の内容を常時確認できるようにします。

- このデモの状態はほかの利用者と共有される。
- 入力した内容が別の利用者にも表示される可能性がある。
- 個人情報、認証情報、実在企業の非公開情報を入力しない。
- 必要であればサンプルを初期状態へリセットできる。

注意文を同意画面として毎回表示する必要はありません。編集操作の近くに置き、読まずに
個人情報を入力する可能性を下げます。

## 4. 入力制限

公開された更新境界へ無制限の入力を渡さないため、Server Actionで次を検証します。

| 入力 | 最大長 | 補足 |
|---|---|---|
| `content` | 5,000文字 | 空文字と現在内容と同一の値も拒否する |
| `reason` | 500文字 | 任意入力。空白だけの場合は未入力として扱う |

改行コードをLFへ統一し、文字列全体の前後にあるUnicode空白だけを除去してから、Unicode
code point単位で文字数を数えます。文字列内部の空白と改行は保持します。HTMLを実行せず、
MVPの`content`と`reason`はプレーンテキストとして表示します。

初期MVPでは外部のrate limitサービスを追加しません。管理可能な人数を超えて公開する場合は、
状態分離と合わせて濫用対策を再検討します。

## 5. 変更競合

編集開始後に別の利用者が同じ業務要素を変更した場合、古い内容をそのまま上書きしません。

1. 編集開始時の`before_version_id`を未確定の変更案とともに保持する。
2. Server Actionへ対象要素、`before_version_id`、変更後の内容、変更理由を渡す。
3. トランザクション内で対象の`business_entities`行をlockする。
4. 現在の最新versionが`before_version_id`と一致することを確認する。
5. 一致する場合だけ、新version、`ChangeSet`、現在内容を更新する。
6. 一致しない場合は何も更新せず、競合を表す型付き結果を返す。

競合時は「ほかの変更が反映されています。最新内容を確認してから、もう一度変更してください」
と表示します。利用者が入力した変更案はClient stateへ残し、最新内容と比較できるようにします。

異なる業務要素への変更は、それぞれ独立したトランザクションとして許可します。

## 6. サンプルリセット

リセットは、共有サンプル状態を
[サンプル業務と検証シナリオ](sample-business-scenario.md)の初期状態へ戻します。

### 6.1 対象

- 現在の`BusinessEntity`
- `Relation`
- 初期versionを含む`EntityVersion`
- すべての`ChangeSet`

### 6.2 実行規則

1. 利用者へ、全利用者の変更内容と変更履歴が削除されることを確認する。
2. Server Actionがリセット処理を開始する。
3. 一つのデータベーストランザクション内で、既存の変更履歴、version、関係、業務要素を
   参照制約に従う順序で削除する。
4. seedから業務要素、関係、`version_number = 1`の初期versionを再作成する。
5. すべて成功した場合だけcommitする。

リセット自体を`ChangeSet`として記録せず、リセット前の履歴は保持しません。MVPのデモ状態を
確実に再現することを、監査履歴より優先します。

リセットによって削除された`BusinessEntity`または`ChangeSet`のURLを開いた場合は、対象が
利用できないことを表示し、初期選択の`rule-receipt-requirement`へ戻れる操作を示します。

## 7. 変更確定とリセットの同時実行

変更確定とリセットは、途中状態が見えないよう、どちらもデータベーストランザクションで
実行します。リセットは対象テーブルへの更新を直列化し、同時に開始した変更確定との実行順を
データベース上で確定させます。

具体的なtable lockまたはtransaction lockの方式は、採用driverでtransaction testを作成して
決定します。要件は次のとおりです。

- 変更確定の一部だけがリセット後に残らない。
- リセット途中の空状態を別requestが現在状態として取得しない。
- リセット完了後は、初期version以外の履歴が存在しない。
- 競合またはlock待ちの失敗を、部分成功として扱わない。

## 8. テストと運用

- E2E testは開始前にリセットし、共有状態を前提として直列実行する。
- リセット後に、12件の業務要素、15件の関係、各要素の初期versionが存在することを確認する。
- 同じ`before_version_id`から二つの変更を確定した場合、一方だけが成功することを確認する。
- リセットと変更確定を同時に実行しても、初期状態または一つの確定済み状態のどちらかへ
  整合することを確認する。
- 公開前に、注意文、入力上限、競合表示、リセット確認をE2Eで確認する。

## 9. 匿名状態へ分離する判断条件

次のいずれかに該当した時点で、共有状態を終了し、cookieなどで識別する匿名workspaceを
検討します。

- 別利用者の変更により、評価者が中核フローを完了できない。
- 管理可能な評価者の範囲を超えてURLを公開する。
- 複数人が同時にデモを操作する検証を行う。
- 利用者ごとの変更結果とフィードバックを対応付ける必要がある。
- 共有状態への濫用対策が、状態を分離するより複雑になる。

状態分離を導入する場合は、先に要件、テーブル設計、ER図、リセットの単位を更新します。
初期MVPのテーブルへ、将来用途だけの`workspace_id`を追加しません。
