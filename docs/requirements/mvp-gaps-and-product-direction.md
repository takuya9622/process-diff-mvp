# MVPの不足点とプロダクト方針

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 文書状態 | 現行MVP反映済み |
| 対象 | 現行MVPで補う価値仮説と、次期検証へ送る論点 |
| 最終更新日 | 2026-08-10 |

この文書では、現行MVPを壊さず、1週間で検証可能な範囲を維持したまま補う設計と、
MVP後に検証する仮説の境界を定義します。機能と受け入れ条件は
[プロダクト要件](product-requirements.md)、画面への反映は
[MVP画面構成とユーザーフロー](../design/screens-and-user-flow.md)を参照してください。

## 2. 今回維持する設計

現行MVPですでに成立している次の設計は変更しません。

- 通常利用を業務知識の参照、変更時だけを変更管理として分離する
- 差分を主ナビゲーションではなく、変更を安全に確定するための確認手段として扱う
- 認証された利用者、操作対象の組織、アクセス権限を明示する
- 組織ごとに業務グラフと変更履歴を分離する
- 登録済みの`Relation`から、断定ではなく影響候補と経路を提示する
- 架空の経費精算サンプルを使い、実在企業の業務データや外部SaaSを取り込まない

## 3. 現行MVPの不足点

| ID | 不足点 | このままの場合のリスク | 今回の扱い |
|---|---|---|---|
| G-01 | 対象顧客が「企業ユーザー」程度で広い | 誰のどの問題を検証するMVPか判断できない | 主ペルソナと対象組織を絞る |
| G-02 | 変更時の価値に比べ、変更しない日の利用理由が弱い | 低頻度ツールに見え、継続利用や月額課金の仮説を検証できない | 通常利用の検証シナリオを中核へ追加する |
| G-03 | 文書ページと種類別一覧が前面に出ており、業務をハブにした理解が弱い | 一般的なナレッジベースとの違いが伝わりにくい | `PROCESS`を入口に周辺要素を理解する画面構造へ直す |
| G-04 | 価値が情報整理と影響候補の説明に留まり、投資対効果へつながる観測項目がない | 「便利そう」という感想だけで検証が終わる | 探索、確認、変更調査、入力負荷の観測項目を定義する |
| G-05 | 完成済みサンプルグラフを使うため、導入直後の価値と登録・維持コストを検証できない | 実運用でBusiness Graphが作られず、価値が立ち上がらない可能性を見落とす | 現MVPの検証限界として明示し、次期仮説へ送る |
| G-06 | 現行`Relation`は確定済みだけを扱い、現実の曖昧な関係を表せない | AI推定を追加したとき、推定を事実として扱う危険がある | Candidate、Evidence、Confidenceの論理境界だけ先に定義する |
| G-07 | 外部SaaS連携、AI推定、健康診断の優先順位が未整理 | 1週間MVPへ大きな機能が混入し、中核仮説がぼやける | 現MVP、次期検証、対象外の3段階へ分ける |

## 4. プロダクト定義

プロダクトの中心を、文書保存や変更履歴ではなく`Business Graph`とします。

> 企業内の複数サービスや人に分散した業務構造を一つのレイヤーとして理解し、日常の
> 情報探索と変更時の影響確認を支援するB2B SaaS。

短い価値説明には、次を使用します。

> 会社の業務を起点に、関係するルール、文書、システム、担当を一か所で理解し、
> 変更するときは確認が必要な範囲を見つける。

現行MVPには外部SaaS接続がないため、「SaaSを接続すれば情報を自動取得できる」とは説明
しません。現MVPで検証するのは、複数の場所に分散し得る情報を業務単位の構造として見る
体験と、変更時にその構造を影響確認へ使う体験です。

## 5. 主ペルソナ

主ペルソナは、従業員30〜300人程度の組織で、業務ルール、手順、業務改善に関わる社員と
します。具体例は、業務改善担当、総務、情報システム担当、管理部門、現場リーダー、
業務オーナー、小規模組織のマネージャーです。

対象とするのは、次の両方に該当する利用者です。

- 会社の業務変更で、確認漏れや手戻りを起こしたくない
- 日常的に、業務情報がどこにあり、誰や何と関係するか分からず困っている

対象組織には、複数のSaaSを利用し、口頭、チャット、文書、フォーム、社内システムへ業務
情報が分散している一方、大企業向けBPMを導入する規模や体制には達していない状態を想定
します。

## 6. 現行MVPへ反映する決定

### 6.1 業務を通常利用の入口にする

- 組織ワークスペースの初期表示は、変更対象の`RULE`ではなく`PROCESS`にする
- 経費精算サンプルでは「経費申請」を通常利用の起点にする
- `PROCESS`詳細では、関連ルール、使用システム、担当・承認、関連文書、前後工程を意味の
  分かるまとまりで表示する
- 関連要素を選択した後も、その要素から業務へ戻り、別の関係をたどれるようにする
- 種類別一覧と検索は探索手段として残すが、文書の保管場所がプロダクトの中心だと見せない

### 6.2 通常利用と変更利用を別の検証シナリオにする

現行MVPでは、次の二つを独立して完了できるようにします。

1. **業務理解シナリオ**: 「経費申請」を開き、変更操作をせず、関係するルール、文書、
   システム、担当・承認者、後工程を確認する
2. **安全な変更シナリオ**: 「領収書提出ルール」を開き、内容を変更し、差分を確認して
   確定し、影響候補と経路を確認する

変更シナリオだけを完了しても、日常価値を検証したことにはしません。

### 6.3 Business Graphを主役にする

通常画面は文書本文だけでなく、その要素が業務構造のどこにあるかを同時に示します。
ただしMVPでは全体グラフ画面やグラフ編集を追加せず、選択中の要素と直接関係を使って
段階的にたどる体験を維持します。

## 7. スコープの境界

| 段階 | 扱う内容 |
|---|---|
| 現行MVP | 組織と利用者の明示、業務中心の参照、検索、直接関係、変更、差分、確定Relationからの影響候補、二つの検証シナリオ |
| 次期検証 | `Source` / External SaaS、SaaS横断表示、Relation Candidate、Evidence、Confidence、業務資産の健康診断、単一SaaSとの読み取り連携 |
| 現時点の対象外 | 複数Connector群、AI完全自動解析、Process Mining、Workflow Automation、BPM Engine、高度な監査、自動的な業務変更 |

次期検証の項目は、現行MVPのテーブル、画面、受け入れ条件へ暗黙に追加しません。検証結果を
もとに一つずつ採否を決めます。

## 8. 現行実装への反映

今回の設計変更は、既存の認証、組織、変更確定、差分、影響探索、テーブル構造を変更せず、
次の通常利用と検証シナリオの変更として反映済みです。

- 初期表示のseed keyを`rule-receipt-requirement`から`process-expense-submission`へ変える
- 業務要素ナビゲーションで`PROCESS`を先頭の入口として維持する
- `PROCESS`の直接関係を、ルール、システム、担当・承認、文書、前後工程に分類して表示する
- `PROCESS`以外では、関係する業務へ戻る導線を先に示す
- E2Eを業務理解シナリオと安全な変更シナリオに分け、両方を検証する

`Source`、Relation Candidate、Evidence、Confidenceの列やtableは追加しません。これらは次期
検証を実装すると決めた時点で、現在の確認済み`Relation`と混同しないデータ設計を行います。

## 9. 次期検証の論理境界

### 9.1 Business Graphを発見する流れ

将来の入力体験は、利用者へ業務要素と関係の全登録を要求するのではなく、次の流れを基本と
します。

```text
External Data
  -> Rule / API / AI Analysis
  -> Relation Candidate
  -> Evidence + Confidence
  -> 必要な候補だけ人が確認
  -> Confirmed Business Graph
```

AIの役割は候補作成と入力削減であり、企業業務の事実を単独で確定することではありません。

### 9.2 Relation Candidate

将来の候補は、少なくとも次の概念を持てる構造として検討します。

```text
Relation Candidate
- source
- target
- type
- status: suggested | inferred | confirmed | rejected
- confidence
- evidence[]
```

Evidenceの候補は`explicit_link`、`api_structure`、`semantic_match`、`usage_pattern`、
`historical_cochange`、`human_confirmation`です。`confidence`だけで確定せず、根拠と状態を
画面で区別できることを必須条件とします。

### 9.3 Time to Value

次期検証では、Business Graphが十分に育つ前にも価値を返す必要があります。最初の候補は、
単一SaaSを読み取り接続した直後に、古い情報、所有者不明、重複、関連候補、複数箇所への
分散を示す「業務資産の健康診断」です。

健康診断は次期仮説であり、現行MVPが実施済みだとは表現しません。

## 10. MVPで観測すること

### 10.1 Product Understanding

- 初見で、文書管理ではなく業務構造を理解するサービスだと説明できるか
- どの組織の誰として操作しているか理解できるか

### 10.2 Daily Value

- 変更せずに、経費申請で使うシステム、従うルール、関係者、文書、後工程を見つけられるか
- 情報探索の入口として使いたいと感じるか
- 既存SaaSを置き換えるのではなく、その上位で関係を理解する構想が伝わるか

### 10.3 Change Value

- 差分が変更内容の確認に役立つか
- 影響候補と経路が、次に確認する項目の洗い出しを助けるか
- 変更前の調査や更新漏れによる手戻りを減らせそうか

### 10.4 Input Cost

- 現実の業務要素と関係を手入力する場合、どこで負担が価値を上回るか
- APIやAIが候補を作り、人が確認する方式なら導入可能性が上がるか

### 10.5 Business Value

- 情報探索、他者への確認、影響調査、更新漏れ、オンボーディングのどれに最も費用対効果を
  感じるか
- 日常利用者、導入責任者、予算保有者は誰か
- 月額費用を、便利ツール代ではなく業務効率化、事故防止、知識維持への投資として説明
  できるか

MVPの評価では「便利そう」という総評だけで終わらせず、二つのシナリオの完了可否、迷った
箇所、探索や確認にかかった時間、入力負荷への反応、最も価値を感じたコストを記録します。

## 11. 設計判断の基準

今後の機能追加では、次の順に確認します。

1. 変更しない日にも、業務を探す・理解する価値が増えるか
2. Business Graphの作成・維持コストを利用者へ押し付けていないか
3. 文書保存や単体SaaSの置き換えではなく、業務構造を扱う機能か
4. 変更時の確認漏れ、調査、手戻りを減らせるか
5. 現在の検証段階で必要か、次期仮説として分離すべきか
