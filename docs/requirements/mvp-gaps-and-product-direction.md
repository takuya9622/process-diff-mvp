# MVPの不足点とプロダクト方針

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 文書状態 | ネイティブ業務実行方針反映済み |
| 対象 | 現行MVPの不足点と、日本企業向けの次段階プロダクト方針 |
| 最終更新日 | 2026-08-10 |

この文書では、実装済みMVPを維持したまま、業務知識の参照と変更から、アプリ内で業務を
完了できる次段階へ進む境界を定義します。現行機能と受け入れ条件は
[プロダクト要件](product-requirements.md)、現行画面は
[MVP画面構成とユーザーフロー](../design/screens-and-user-flow.md)、次段階の詳細は
[ネイティブ業務ワークフロー設計](../design/native-business-workflows.md)を参照してください。

## 2. 今回維持する設計

現行MVPですでに成立している次の設計は変更しません。

- 通常利用を業務知識の参照、変更時だけを変更管理として分離する
- 差分を主ナビゲーションではなく、変更を安全に確定するための確認手段として扱う
- 認証された利用者、操作対象の組織、アクセス権限を明示する
- 組織ごとに業務グラフと変更履歴を分離する
- 登録済みの`Relation`から、断定ではなく影響候補と経路を提示する
- 架空の経費精算サンプルを使い、実在企業の業務データや外部SaaSを取り込まない

## 3. 現行MVPの不足点

| ID | 不足点 | このままの場合のリスク | 今回の扱い |
|---|---|---|---|
| G-01 | 対象顧客が「企業ユーザー」程度で広い | 誰のどの問題を検証するMVPか判断できない | 主ペルソナと対象組織を絞る |
| G-02 | 変更時の価値に比べ、変更しない日の利用理由が弱い | 低頻度ツールに見え、継続利用や月額課金の仮説を検証できない | 通常利用の検証シナリオを中核へ追加する |
| G-03 | 文書ページと種類別一覧が前面に出ており、業務をハブにした理解が弱い | 一般的なナレッジベースとの違いが伝わりにくい | `PROCESS`を入口に周辺要素を理解する画面構造へ直す |
| G-04 | 価値が情報整理と影響候補の説明に留まり、投資対効果へつながる観測項目がない | 「便利そう」という感想だけで検証が終わる | 探索、確認、変更調査、入力負荷の観測項目を定義する |
| G-05 | 完成済みサンプルグラフを使うため、導入直後の価値と登録・維持コストを検証できない | 実運用でBusiness Graphが作られず、価値が立ち上がらない可能性を見落とす | 現MVPの検証限界として明示し、次期仮説へ送る |
| G-06 | 現行`Relation`は確定済みだけを扱い、現実の曖昧な関係を表せない | AI推定を追加したとき、推定を事実として扱う危険がある | Candidate、Evidence、Confidenceの論理境界だけ先に定義する |
| G-07 | 外部SaaS連携、AI推定、業務実行の優先順位が未整理 | Connectorがないと価値が出ない構成や、大きな機能の同時実装になる | ネイティブ業務実行を先にし、APIとAIを後段へ分ける |
| G-08 | 現行MVPは業務を理解・変更できても、その業務を実行できない | 実務では申請、作業、承認のため別サービスへ移動し、日常利用の中心にならない | 案件、タスク、承認、期限、証跡を次段階の正規ドメインにする |

## 4. プロダクト定義

プロダクトの中心を、文書保存や外部サービスへのリンクではなく、業務の知識、実行、変更を
一つにつなぐ構造とします。

> 企業の業務を、関係するルール、文書、役割とともに理解し、申請、作業、承認、完了まで
> 実行し、変更するときは差分と影響を確認できるB2B SaaS。

短い価値説明には、次を使用します。

> 会社の業務を理解する場所と、実際に進める場所を一つにする。誰が次に何をするかを明確にし、
> 業務を変えるときは確認が必要な範囲を見つける。

`Business Graph`は、業務の背景、根拠、関係を表す知識層として維持します。次段階では、
版管理された業務定義と、一回ごとの案件、タスク、承認、判断、証跡を加えます。外部APIは
このネイティブドメインへ入出力する手段であり、業務の正本にはしません。

現行MVPには業務実行と外部SaaS接続がないため、実装済み機能として説明しません。現MVPで
検証するのは、分散し得る情報を業務単位で理解し、変更時に影響確認へ使う体験です。

## 5. 主ペルソナ

主ペルソナは、従業員30〜300人程度の組織で、業務ルール、手順、業務改善に関わる社員と
します。具体例は、業務改善担当、総務、情報システム担当、管理部門、現場リーダー、
業務オーナー、小規模組織のマネージャーです。

次段階では、上記の設計・管理者だけでなく、申請者、担当者、承認者を日常利用者に含めます。
業務設計の専門知識がなくても、自分の担当、期限、案件の現在地、次の行動を理解できることを
利用条件とします。

対象とするのは、次の両方に該当する利用者です。

- 会社の業務変更で、確認漏れや手戻りを起こしたくない
- 日常的に、業務情報がどこにあり、誰や何と関係するか分からず困っている

対象組織には、複数のSaaSを利用し、口頭、チャット、文書、フォーム、社内システムへ業務
情報が分散している一方、大企業向けBPMを導入する規模や体制には達していない状態を想定
します。

## 6. 現行MVPへ反映する決定

### 6.1 業務を通常利用の入口にする

- 組織ワークスペースの初期表示は、変更対象の`RULE`ではなく`PROCESS`にする
- 経費精算サンプルでは「経費申請」を通常利用の起点にする
- `PROCESS`詳細では、関連ルール、使用システム、担当・承認、関連文書、前後工程を意味の
  分かるまとまりで表示する
- 関連要素を選択した後も、その要素から業務へ戻り、別の関係をたどれるようにする
- 種類別一覧と検索は探索手段として残すが、文書の保管場所がプロダクトの中心だと見せない

### 6.2 通常利用と変更利用を別の検証シナリオにする

現行MVPでは、次の二つを独立して完了できるようにします。

1. **業務理解シナリオ**: 「経費申請」を開き、変更操作をせず、関係するルール、文書、
   システム、担当・承認者、後工程を確認する
2. **安全な変更シナリオ**: 「領収書提出ルール」を開き、内容を変更し、差分を確認して
   確定し、影響候補と経路を確認する

変更シナリオだけを完了しても、日常価値を検証したことにはしません。

### 6.3 Business Graphを主役にする

通常画面は文書本文だけでなく、その要素が業務構造のどこにあるかを同時に示します。
ただしMVPでは全体グラフ画面やグラフ編集を追加せず、選択中の要素と直接関係を使って
段階的にたどる体験を維持します。

## 7. スコープの境界

| 段階 | 扱う内容 |
|---|---|
| 現行MVP | 組織と利用者の明示、業務中心の参照、検索、直接関係、変更、差分、確定Relationからの影響候補、二つの検証シナリオ |
| 次の実装段階 | 経費申請・精算処理を使ったネイティブな案件、構造化入力、タスク、承認、差し戻し、期限、Activity、完了証跡 |
| 後続検証 | 汎用workflow定義、複数step、並列承認、組織・代理、schedule、業務定義のreviewと公開 |
| Integration段階 | 外部triggerとaction、Connector、項目mapping、同期状態、Relation Candidate、Evidence、Confidence、AI支援 |
| 現時点の対象外 | AIによる重要判断の自動確定、Process Mining、規制準拠を保証する監査、実行中案件の暗黙移行 |

次段階の項目は、現行MVPのテーブル、画面、受け入れ条件へ暗黙に追加しません。実装する段階で
対象要件、schema、画面、migration、testを同じ変更単位で設計します。

## 8. 現行実装への反映

今回の設計変更は、既存の認証、組織、変更確定、差分、影響探索、テーブル構造を変更せず、
次の通常利用と検証シナリオの変更として反映済みです。

- 初期表示のseed keyを`rule-receipt-requirement`から`process-expense-submission`へ変える
- 業務要素ナビゲーションで`PROCESS`を先頭の入口として維持する
- `PROCESS`の直接関係を、ルール、システム、担当・承認、文書、前後工程に分類して表示する
- `PROCESS`以外では、関係する業務へ戻る導線を先に示す
- E2Eを業務理解シナリオと安全な変更シナリオに分け、両方を検証する

`WorkflowDefinition`、`Case`、`WorkItem`、`Approval`、`Source`、Relation Candidate、Evidence、
Confidenceの列やtableは現行実装へ追加していません。これらは対象段階の実装を開始するときに、
現行の知識・変更ドメインと混同しないデータ設計を行います。

## 9. 次段階の論理境界

### 9.1 ネイティブ業務実行を先に成立させる

次段階では外部サービスから業務を組み立てるのではなく、確認済みの業務知識から実行可能な
定義を作り、アプリ内で案件を完了する流れを先に検証します。

```text
Confirmed Business Graph
  -> Versioned Workflow Definition
  -> Case
  -> Work Item / Approval / Decision
  -> Activity + Evidence
  -> Completed Business Result
```

最初の経費申請では、開始、構造化入力、担当、承認、差し戻し、再申請、精算処理の記録、完了を
ネイティブに扱います。外部APIがなくても、この一連の状態と責任主体を失わずに業務を完了
できることを優先します。

### 9.2 外部APIはネイティブドメインへ接続する

Integration段階では、外部イベントとrecordを直接workflowの正本にせず、Connectorで
ネイティブな開始要求、案件データ、タスク、判断、文書、予定、通知へ変換します。

```text
External Event / Record
  <-> Connector + Mapping + Sync State
  <-> Native Case / Work Item / Decision / Artifact
```

Connector固有の認証、payload、外部ID、rate limit、再試行はIntegration層へ閉じ込めます。
外部同期が失敗しても案件の現在状態と人の判断を失わず、必要なら手動で業務を継続できることを
設計条件とします。

コミュニケーションも同じ原則に従います。組織内Channel、Message、任意のCase参照を先に
ネイティブ実装し、Slack channelまたはGoogle Chat spaceとの対応、外部message ID、cursor、
retry、同期方向はConnector mappingへ分離します。外部接続が停止しても、アプリ内の投稿と
案件参照を継続できることを必須条件とします。

### 9.3 Business Graphを発見する流れ

外部データやAIから業務知識を発見する構想は、ネイティブ業務実行の後続仮説として維持します。
利用者へ業務要素と関係の全登録を要求せず、次の流れで確認済みBusiness Graphへ反映します。

```text
External Data
  -> Rule / API / AI Analysis
  -> Relation Candidate
  -> Evidence + Confidence
  -> 必要な候補だけ人が確認
  -> Confirmed Business Graph
```

Relation Candidateは、少なくとも`source`、`target`、`type`、`status`、`confidence`、`evidence[]`を
持てる構造として検討します。`status`は`suggested`、`inferred`、`confirmed`、`rejected`を候補と
します。AIの役割は候補作成と入力削減であり、企業業務の事実や重要判断を単独で確定すること
ではありません。

### 9.4 Time to Value

利用者へ最初から汎用workflowを設計させず、完成済みの経費申請templateから案件を開始できる
ようにします。日常利用者が申請と承認を完了して価値を確認した後、業務設計者がrule、担当、
期限を自社向けに変更する順序を基本とします。

単一SaaS接続直後の業務資産の健康診断は後続仮説として残しますが、次の実装段階の入口には
しません。

## 10. 検証段階で観測すること

### 10.1 Product Understanding

- 初見で、文書管理ではなく業務構造を理解するサービスだと説明できるか
- どの組織の誰として操作しているか理解できるか

### 10.2 Daily Value

- 変更せずに、経費申請で使うシステム、従うルール、関係者、文書、後工程を見つけられるか
- 情報探索の入口として使いたいと感じるか
- 現行MVPで、分散した情報を業務単位で理解する構想が伝わるか

### 10.3 Operational Value

- 外部連携なしで、経費申請の開始、承認、差し戻し、再申請、精算処理の記録、完了をアプリ内で行えるか
- 利用者が案件の現在地、次の担当者、期限、経路の理由を説明できるか
- 申請者、担当者、承認者が、業務設計の専門知識なしで自分の操作を完了できるか
- 別サービスへの転記、進捗確認、担当者への催促を減らせそうか
- 組織内チャンネルで案件を共有し、会話から同じ案件へ戻れるか

### 10.4 Change Value

- 差分が変更内容の確認に役立つか
- 影響候補と経路が、次に確認する項目の洗い出しを助けるか
- 変更前の調査や更新漏れによる手戻りを減らせそうか

### 10.5 Input Cost

- 現実の業務要素と関係を手入力する場合、どこで負担が価値を上回るか
- 完成済みtemplateを自社向けに調整する場合、どの設定から専門支援が必要になるか
- APIやAIが候補を作り、人が確認する方式なら導入可能性が上がるか

### 10.6 Business Value

- 情報探索、進捗確認、承認待ち、転記、影響調査、更新漏れ、オンボーディングのどれに最も
  費用対効果を感じるか
- 日常利用者、導入責任者、予算保有者は誰か
- 月額費用を、便利ツール代ではなく業務効率化、事故防止、知識維持への投資として説明
  できるか

現行MVPの評価では二つのシナリオ、次段階では経費申請の実行シナリオを分けて観測します。
「便利そう」という総評だけで終わらせず、完了可否、迷った箇所、所要時間、入力・設定負荷、
例外時の理解、最も価値を感じたコストを記録します。

## 11. 設計判断の基準

今後の機能追加では、次の順に確認します。

1. 外部連携がなくても、利用者が業務を開始から完了まで進められるか
2. 利用者が現在地、次の行動、担当、期限、判断理由を理解しやすくなるか
3. 業務知識、業務定義、実行案件、変更履歴を一貫して扱う機能か
4. Business Graphやworkflowの作成・維持コストを利用者へ押し付けていないか
5. 変更時の確認漏れ、調査、手戻りを減らせるか
6. 外部APIやAIを追加しても、業務の正本と人の責任がアプリ内に残るか
7. 現在の検証段階で必要か、後続仮説として分離すべきか
