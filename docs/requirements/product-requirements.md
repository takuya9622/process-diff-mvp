# プロダクト要件

この文書では、MVPの機能要件、非機能要件、UX要件、受け入れ条件を定義します。
サービスの目的と対象範囲は[要件定義の入口](README.md)を参照してください。

この文書の要件IDは、業務知識参照、安全な変更、最初のネイティブ経費申請を対象とします。
業務実行の拡張方針は
[ネイティブ業務ワークフロー設計](../design/native-business-workflows.md)で定義します。

## 1. 機能要件

優先度は、`必須`、`推奨`、`将来`の3段階で表します。

### 1.1 業務要素の参照

| ID | 要件 | 優先度 |
|---|---|---|
| FR-001 | 利用者はサンプルの業務要素を一覧表示できる | 必須 |
| FR-002 | 利用者は業務要素の名称、種類、説明、現在の内容を確認できる | 必須 |
| FR-003 | 利用者は業務要素から直接関係する要素を確認できる | 必須 |
| FR-004 | 利用者は種類によって業務要素を識別できる | 推奨 |
| FR-005 | 利用者は編集や変更履歴を経由せず、現在の業務知識を一覧、詳細、関係からたどれる | 必須 |
| FR-006 | 利用者は長い業務知識を、見出し、本文、リスト、ページ内目次として読める | 必須 |
| FR-007 | 利用者は名称、説明、種類から業務要素を検索できる | 推奨 |
| FR-008 | 利用者は`PROCESS`を入口に、関連ルール、文書、システム、担当・承認、前後工程を業務単位で確認できる | 必須 |

### 1.2 業務要素の変更

| ID | 要件 | 優先度 |
|---|---|---|
| FR-101 | 利用者は一つの業務要素の内容を編集できる | 必須 |
| FR-102 | システムは編集前の状態を保持できる | 必須 |
| FR-103 | システムは一回の操作を一つの変更単位として扱える | 必須 |
| FR-104 | 利用者は変更を確定する前に内容を確認できる | 推奨 |
| FR-105 | 利用者は変更理由を入力できる | 推奨 |
| FR-106 | システムは利用者が明示的に編集を開始したときだけ変更フローへ切り替える | 必須 |
| FR-107 | 変更フローは本文、変更案の概要、差分、反映状態を分離して表示する | 必須 |

### 1.3 差分表示

| ID | 要件 | 優先度 |
|---|---|---|
| FR-201 | 利用者は変更前と変更後の内容を比較できる | 必須 |
| FR-202 | 追加、削除、変更された箇所を視覚的に識別できる | 必須 |
| FR-203 | Gitの知識がなくても差分の意味を理解できる表現を使う | 必須 |
| FR-204 | 差分を通常利用の主ナビゲーションにせず、変更の確認と確定済み結果の再表示に限定する | 必須 |
| FR-205 | 長い変更なし区間は前後の文脈を残して折りたたみ、必要な場合だけ展開できる | 推奨 |

### 1.4 影響候補の提示

| ID | 要件 | 優先度 |
|---|---|---|
| FR-301 | システムは変更された業務要素を起点に関係グラフを探索できる | 必須 |
| FR-302 | システムは探索結果を影響候補として提示できる | 必須 |
| FR-303 | 利用者は各候補が提示された理由または関係経路を確認できる | 必須 |
| FR-304 | システムは影響を断定せず、確認が必要な候補として表現する | 必須 |
| FR-305 | 利用者は重要な候補を識別しやすい順序で確認できる | 推奨 |
| FR-306 | 利用者は変更元、直接関係、2段階先の配置で候補全体のつながりを確認できる | 推奨 |

### 1.5 デモ体験

| ID | 要件 | 優先度 |
|---|---|---|
| FR-401 | 第三者は公開URLから利用者登録し、自分の業務スペースでMVPを試せる | 必須 |
| FR-402 | 初期表示時点で関係を持つサンプル業務が用意されている | 必須 |
| FR-403 | 利用者が迷わず中核フローを完了できる案内を用意する | 推奨 |
| FR-404 | 利用者はサンプルデータを初期状態へ戻せる | 推奨 |
| FR-405 | 第三者は、変更しない業務理解と安全な変更の二つのシナリオを独立して完了できる | 必須 |

### 1.6 利用者、認証、組織

| ID | 要件 | 優先度 |
|---|---|---|
| FR-501 | 利用者は名前、メールアドレス、パスワードで登録できる | 必須 |
| FR-502 | 利用者はメールアドレスとパスワードでサインインできる | 必須 |
| FR-503 | 利用者はサインアウトできる | 必須 |
| FR-504 | 初回利用者は組織名を入力して自分の業務スペースを作成できる | 必須 |
| FR-505 | システムは業務データと変更履歴を組織ごとに分離する | 必須 |
| FR-506 | システムは、利用者が所属しない組織のデータ参照と更新を拒否する | 必須 |
| FR-507 | 利用者は現在の組織、自分の名前、アクセス権限を常時確認できる | 必須 |
| FR-508 | 変更履歴は変更を確定した利用者を記録・表示できる | 必須 |
| FR-509 | `owner`と`editor`は変更を確定でき、`viewer`は参照だけできる | 必須 |
| FR-510 | `owner`だけが現在の組織のサンプルをリセットできる | 必須 |
| FR-511 | 一組織のリセットは、ほかの組織と認証・所属データへ影響しない | 必須 |
| FR-512 | メール確認とパスワード再設定をMVPの対象外として利用者へ誤認させない | 推奨 |
| FR-513 | システムは組織ロールと業務要素の`ROLE`を別概念として表示する | 必須 |

### 1.7 ネイティブ業務実行

| ID | 要件 | 優先度 |
|---|---|---|
| FR-601 | 利用者は公開済みの業務から経費申請を開始できる | 必須 |
| FR-602 | 利用者は経費発生日、金額、用途、支払先、領収書参照情報を入力し、下書き保存または申請できる | 必須 |
| FR-603 | システムは案件を開始時点のWorkflowVersionへ固定し、現在地、次の担当、期限を表示できる | 必須 |
| FR-604 | 担当承認者は申請内容と判断の根拠を確認し、承認、却下、差し戻しを記録できる | 必須 |
| FR-605 | 差し戻しと却下では理由を必須とし、承認を含む判断履歴を同じ案件へ保持する | 必須 |
| FR-606 | 処理済みWorkItemからの二重判断を拒否し、案件状態を変更しない | 必須 |
| FR-607 | 申請者は差し戻し理由を確認し、同じ案件の入力を修正して再申請できる | 必須 |
| FR-608 | 担当経理者は処理日、参照番号、処理結果・証跡を記録して案件を完了できる | 必須 |
| FR-609 | 完了、却下、取消後も案件の入力、適用version、判断、Activity、結果を再表示できる | 必須 |
| FR-610 | 外部APIまたはConnectorがなくても、経費申請を開始から完了までアプリ内で処理できる | 必須 |
| FR-611 | 案件と作業から、判断根拠となる既存の業務知識を確認できる | 必須 |
| FR-612 | ownerとeditorだけが案件を更新でき、viewerは参照だけできる | 必須 |
| FR-701 | 主ナビゲーションをダッシュボード、ワークフロー、規定・文書、コミュニケーションの責務に分ける | 必須 |
| FR-702 | ownerとeditorは組織内チャンネルを作成し、メッセージを投稿できる | 必須 |
| FR-703 | 利用者はメッセージへ自組織の案件を添付し、同じ組織の案件詳細へ移動できる | 必須 |
| FR-704 | チャンネルとメッセージを外部providerに依存しない正規データとして保存する | 必須 |
| FR-705 | SlackまたはGoogle Chat未接続でも、チャンネル作成、投稿、案件共有をアプリ内で完了できる | 必須 |

## 2. 非機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| NFR-001 | 第三者が公開URLから利用者登録して利用できる | 必須 |
| NFR-002 | サンプルデータに個人情報や実在企業の非公開情報を含めない | 必須 |
| NFR-003 | 主要画面は一般的なデスクトップ環境で利用できる | 必須 |
| NFR-004 | Gitを知らない利用者も主要な操作と表示を理解できる | 必須 |
| NFR-005 | 同じ入力と関係データから同じ影響候補を再現できる | 必須 |
| NFR-006 | サンプル規模では、一覧、差分、影響候補を待たされたと感じにくい時間で表示する | 推奨 |
| NFR-007 | キーボード操作、見出し構造、色以外の差分表現など基本的なアクセシビリティを考慮する | 推奨 |
| NFR-008 | 確定済みの変更内容と履歴は、ブラウザ更新後も保持する | 推奨 |
| NFR-009 | 認証済み利用者は、自分が所属する組織のデータだけを取得・更新できる | 必須 |
| NFR-010 | パスワードの平文、session token、認証secretを保存・ログ出力・画面表示しない | 必須 |
| NFR-011 | 認証と権限の判定は、クライアント表示だけでなくサーバー側の取得・更新境界で行う | 必須 |
| NFR-012 | 認証endpointはCSRF・origin検証とrate limitを有効にする | 必須 |

## 3. UX要件

- 通常利用では、業務知識を探す、読む、関係をたどる体験を中心にする
- 通常利用の入口では`PROCESS`を優先し、業務に関係するルール、文書、システム、役割、
  前後工程を意味の分かるまとまりで表示する
- 通常利用は長文ページ、ページ内目次、種類別ナビゲーション、検索を中心とし、編集欄を常設しない
- 主ナビゲーションはダッシュボード、ワークフロー、規定・文書、コミュニケーションへ分け、
  業務要素の種類別一覧は規定・文書を開いた場合だけ二次ナビゲーションとして表示する
- 編集操作を、通常の知識参照から変更フローへ入る明示的な境界にする
- 変更時はPull Requestに似た情報設計で、本文編集、変更案の概要、差分レビュー、反映操作を段階化する。ただしGit用語の知識は要求しない
- 差分は独立した閲覧モードではなく、変更前の誤操作防止と変更結果の説明に使う
- 変更完了後は、確認が必要な項目から業務知識の参照へ戻れる導線を用意する
- 内部のグラフ構造やバージョン管理の複雑さを、そのまま利用者へ見せない
- `commit`、`branch`、`pull request`、`merge`などのGit用語を操作理解の前提にしない
- 「業務」「変更」「変更前・変更後」「関連項目」「影響候補」「確認」などの表現を使う
- 変更箇所と影響候補を、同じ操作の流れの中で確認できる
- 影響候補には、候補になった理由を添えて利用者の判断を支援する
- 影響候補はコンパクトな関係一覧と、変更元から2段階先までに限定した簡易グラフを連動させる
- 警告を過剰に表示せず、検出数よりも理解しやすさを優先する
- ヘッダーで「どの組織の、誰として、どの権限で操作しているか」を常時示す
- 「業務を起点に全体像を理解し、必要なときは安全に変更できる」という価値を
  操作前から示す
- 組織へのアクセス権限と、業務グラフ内の申請者・承認者などの役割を混同させない
- 文書の保存場所ではなく、業務構造と関係を理解するサービスだと通常画面だけで判断できる
- 外部SaaS連携がない現行MVPで、接続や自動取り込みができると誤認させない
- 日常利用の入口では、自分の対応待ちと最近の案件を優先し、一回の選択で担当作業を開ける
- 承認、差し戻し修正、経理処理を、案件の現在地と申請内容を保った同じ文脈で完了できる
- 状態、期限超過、判断結果を色だけに依存せず文字でも説明する
- 会話から共有案件へ戻れる導線を用意し、案件番号と状態を文字で表示する
- 外部連携が未実装の間は、メッセージがアプリ内だけへ保存されることを明示する

## 4. 受け入れ条件

MVPは、次の条件をすべて満たしたときに中核フローが成立したと判断します。

1. 公開URLから利用者登録、初回組織作成、サインイン、サインアウトを完了できる。
2. 利用者が現在の組織、自分の名前、アクセス権限を確認できる。
3. 通常利用時に、変更操作をせず自分の組織の業務要素と関係をたどって理解できる。
4. 通常利用の主ナビゲーションに差分や変更履歴が表示されない。
5. 変更権限を持つ利用者が明示的に編集を開始すると、変更フローへ移れる。
6. 利用者が変更を確定する前に、変更前と変更後の差分を確認できる。
7. 利用者が変更に関連する影響候補と、その理由または関係経路を確認できる。
8. 変更履歴から変更者と変更日時を確認できる。
9. 別組織のURLやIDを指定しても、その組織のデータを取得・更新できない。
10. 一組織のリセットが、ほかの組織と認証・所属データへ影響しない。
11. 主要な体験をGitの知識なしで完了できる。
12. 複数節からなる長文の業務知識を通常画面で読み、変更時だけページ全体の編集と差分確認へ移れる。
13. 影響候補の一覧と簡易グラフで同じ候補を選択し、最短経路を確認できる。
14. 「経費申請」を入口に、変更操作をせず、関係するルール、文書、使用システム、担当・承認者、後工程を確認できる。
15. 業務理解シナリオを完了した後に、別の操作として「領収書提出ルール」の変更シナリオを開始できる。
16. 経費申請を下書き保存または申請し、ブラウザ更新後も同じ案件を再表示できる。
17. 承認者が差し戻し、申請者が同じ案件を修正して再申請し、二回の判断履歴を確認できる。
18. 承認後、経理担当者が処理結果と証跡を記録し、案件を完了できる。
19. 完了案件で適用workflow version、申請値、承認理由、経理結果、Activityを確認できる。
20. 外部APIなしで16〜19を完了でき、処理済み作業の再実行と別組織からの参照・更新を拒否できる。
21. サイドバーからダッシュボード、業務開始、自分の案件、規定・文書、コミュニケーションを識別して移動できる。
22. 組織内チャンネルを作成し、メッセージへ案件を添付して投稿し、投稿から案件詳細へ戻れる。
23. SlackまたはGoogle Chat未接続でも21〜22を完了でき、別組織のチャンネルと案件を投稿へ混在させない。
